# Mercek

**Design-stage risk pre-screening.** Upload a project report or thesis and Mercek
reads the technologies and data flows it describes, then lists the points that need
to be verified from a security, data leakage and legal liability perspective, each
one with its source.

Mercek works on the document, not the code, so its output is phrased as checks rather
than verdicts: instead of "there is a vulnerability", it says "this technology handles
data this way, check how it is configured in your project". Four agents (extractor,
retriever, analyst, verifier) run on LangGraph, backed by a knowledge base built from
OWASP ASVS, CWE, LINDDUN, KVKK and GDPR. Every finding is tied to both a quote from
the document and a clause from a standard. Findings without that grounding never
reach the user.

Mercek is designed for Turkish-language reports, so its interface and findings are in
Turkish.

## Quick start

Step-by-step guide: **[SETUP.md](SETUP.md)** (~45 minutes, mostly
download time, ~6 GB in total).

```bash
git clone https://github.com/cgrayd/mercek.git
cd mercek
```

**With Docker**

```bash
docker compose up -d qdrant ollama
docker compose exec ollama ollama pull qwen3.5:4b
docker compose up -d backend
docker compose exec backend python -m app.knowledge.ingest
```

**Manual**

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m app.knowledge.ingest    # 37-entry seed knowledge base
python -m app.dogrula             # checks the installation under seven headings
uvicorn app.main:app --reload

cd ../frontend && npm install && npm run dev
```

UI at `http://localhost:5173` · API at `http://localhost:8000/docs`

After the first setup, on Windows you can just double-click **`baslat.bat`**. No
config file is needed; the defaults are correct for a local install
([`config.py`](backend/app/config.py)).

| Hardware | Model | Expected speed |
|---|---|---|
| 16 GB RAM, no GPU | `qwen3.5:4b` | ~10-15 tok/s |
| 32 GB RAM, no GPU | `qwen3.5:9b` | ~4-6 tok/s |
| GPU with 16 GB VRAM | `gpt-oss:20b` | ~40+ tok/s |

## How it works

In classic RAG the user asks a question and the system pulls passages from a document
pool. Here **the uploaded thesis is the input under analysis, not a knowledge source**.
Queries are generated by the agents from the document, not typed by the user. The
document is never written to a vector index; if it were, its own sentences would come
back as "evidence" and the system would end up confirming itself.

The pipeline runs in two waves. Deterministic nodes finish in seconds and publish
their results over SSE right away. LLM nodes take minutes and **add** to those
results. Even if the LLM side fails entirely, the deterministic findings stay.

```
WAVE 1 (no LLM)   ayristir → cikar_sozluk → getir → analiz → dogrula
                                                                ↓ SSE
WAVE 2 (LLM)      ozetle → yonlendir → cikar_llm → getir2 ⇄ sorgu_yaz
                                                      ↓      (≤3 rounds)
                                                   analiz2 → dogrula2
```

## Design decisions

| Decision | Rationale |
|---|---|
| **Qdrant** | Dense and sparse vectors in a single collection, with RRF fusion on the server side. The `kaynak_turu` filter matters: without it, a technical query can return legal text. |
| **BGE-M3** | Dense and sparse from one model. The dense vector captures meaning, the sparse vector catches technical tokens like `CWE-311` or `AES-256`. Strong at matching Turkish documents to English standards. |
| **ASVS, not Top 10** | Top 10 is categorical and coarse, which leads to empty findings like "possible A01 risk". Every ASVS item is an atomic, verifiable requirement. |
| **LINDDUN + CWE + KVKK/GDPR** | Privacy threat modelling, weakness definitions and the legal side, respectively. ASVS covers technical controls, LINDDUN covers privacy. |
| **Local LLM** | The uploaded document may be unpublished. A data leakage analysis tool that sends its input to a third party would undermine its own purpose. |
| **Structured output** | Ollama `format` and `response_format` on OpenAI-compatible endpoints enforce the schema during decoding. Invalid JSON cannot be produced, and the project has no free-text parsing. |
| **LangGraph** | A free-form ReAct agent is not deterministic. The developer defines the flow; autonomy is limited to one controlled loop (query rewriting when retrieval is weak, up to 3 rounds). |

Three decisions are worth explaining in more detail.

**The relevance gate sits *before* fusion.** RRF scores are rank based (`1/(k+rank)`),
not similarity scores, so a threshold applied after fusion cannot filter out an
irrelevant entry. The cosine threshold is applied to the dense pre-fetch and the fused
result is narrowed to that set.

**The deterministic gazetteer runs alongside the LLM, not underneath it.** If
"Firebase" is missed in the thesis, no later stage can recover it.
[`gazetteer.py`](backend/app/core/gazetteer.py) guarantees this with 57 technology
entries, and **Turkish inflectional suffixes are listed explicitly**, since a plain
word boundary misses forms like "Çocukların", "konumu" or "Docker'da". Derivational
suffixes are intentionally left out: "çocukların" matches, "çocukluk" does not.

**Hallucination defense has three layers.** A mechanical check (was the cited source
actually retrieved), a deterministic topic gate (a privacy finding is off-topic if the
document contains no personal data), then an LLM review. Citation fields are also
locked at the schema level: IDs are turned into an enum and become part of the
grammar, so the model cannot produce one that is not on the list. Rejected findings
are shown to the user along with the reason.

Document content is always passed to the model as data, wrapped in
`<<<BELGE_ICERIGI>>>` delimiters ([`llm.py`](backend/app/core/llm.py)), because the
uploaded file might say "ignore previous instructions".

## Project structure

```
backend/app/
  config.py        All settings and their defaults (MERCEK_ prefix)
  schemas.py       Data contract: both the API response and the LLM output schema
  dogrula.py       python -m app.dogrula, installation check
  api/routes.py    HTTP endpoints, live SSE stream
  core/            parsing · gazetteer · embeddings · vectorstore · llm · sablon
  graph/           state · nodes (four agents) · pipeline (two-wave flow)
  knowledge/       seed_data (37 entries) · ingest (ASVS 5.0 support)
backend/degerlendirme/   Quality benchmark: 4 test documents + expected output
frontend/src/            App · api (reconnecting SSE) · components/
```

Good places to start reading: [`graph/pipeline.py`](backend/app/graph/pipeline.py)
(the shape of the flow) and [`schemas.py`](backend/app/schemas.py) (the pipeline's
contract).

## Quality measurement

```bash
cd backend
python -m degerlendirme.olcek --hizli --ozetsiz   # no LLM, seconds
python -m degerlendirme.olcek                      # full pipeline, minutes
```

The `temiz_*` documents contain no personal data, so every finding on them is a false
positive. The `tuzak*` documents have embedded risks that must be reported, so every
missed trap is a loss. The two numbers should be read together: a tool that flags
everything would also catch every trap.
